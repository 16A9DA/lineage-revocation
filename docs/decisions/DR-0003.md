## 1. Scope of artifact-key separation

The artifact-signing key must never be held by the distribution service or by any principal the threat model allows to be compromised. Every lineage subject key is held by an agent, and every agent is a potentially compromised intermediary. An artifact key equal to any subject key, including a leaf's, would hand revocation-state forgery to an agent.

The verifier therefore compares the artifact key against the configured root key, every subject key in the presented lineage, and every statement-signing key in the artifact. This enumerates the ruling; it does not widen it. Statement keys are mostly parent subject keys, so an explicit list without subject keys would leave exactly the leaf keys uncovered.

- Keys are compared by canonical encoded key bytes (Option K encoding), not by object identity.
- The verification-time check sees only the presented chain and statements. The normative requirement lives at key generation (the dedicated-key discipline of ruling 3). The verifier check is detection.
- Honestly generated random keys never collide, so an observed match is evidence of misconfiguration or attack. The rejection carries an alert (`artifact_key_reuse`), not only a denial. No unavailable-status policy can excuse it.

## 2. Dividing principle for statement defects

> The verifier escalates to artifact-level rejection exactly those defects that the ingestion contract obliges the service to reject and that the verifier can detect without any authorization semantics.

Statement identifiers are recomputed, never trusted. The verifier computes SHA-256 over the canonical unsigned statement body (excluding the id) and keys everything on that value. The wire `revocation_id` stays (frozen Spec §8) as a reference whose presence and equality are checked.

| category | defects | handling |
|---|---|---|
| **artifact integrity** (wire-malformed) | malformed CBOR or invalid wire structure; missing required fields (`reason_code` is optional, frozen Spec §8); a received payload that is not the exact canonical encoding of its content (including a non-canonical embedded node envelope); incorrect field types; missing, wrongly typed or not-64-byte Ed25519 signature member; missing `revocation_id`; `revocation_id` different from the recomputed id; conflicting duplicates (same recomputed id, different unsigned body) | reject the entire signed artifact; no persistent mutation; alert `artifact_integrity` (field `defect`: `malformed_wire`, `signature_malformed`, `revocation_id_missing`, `revocation_id_mismatch`, `conflicting_duplicate`); reason `ARTIFACT_INTEGRITY`; then the request verdict follows the policy (section 3) |
| **identical statements** | same unsigned body, including different valid signatures over it | deduplicate deterministically and log; one semantic revocation |
| **per-statement semantic** | a correctly formed 64-byte signature that fails verification under the §9 key; unauthorized revoker or scope; target id or lineage mismatch; invalid target lineage | ignore the statement, log, alert `invalid_revocation_statement` (field `reason_code`), continue with the others (frozen Spec §11) |

Why whole-artifact rejection does not contradict the ignore-invalid-statements rule: that rule exists because statements could be injected by unauthorized parties, so rejecting an artifact over them would be a denial-of-service vector. After Revision A only the revocation authority can produce a signed artifact. A wire-malformed statement or a structural conflict inside one is a SHA-256 collision or an integrity failure in the signing pipeline: evidence of authority fault or compromise, the same category as equivocation, and it gets the same policy. Detecting it needs no authorization semantics. Semantic failures need the §9 key derivation and scope rules, and statement authors are delegators, not the artifact authority; one delegator's garbage must not take down the feed.

**Enforcement layers.** The principle obliges the status service to reject these defects at ingestion so well-formed artifacts never contain them, and the verifier re-checks because the service is trusted only for availability. **No status-service ingestion layer exists in this repository (D19, deferred); only the verifier layer is implemented and tested.** Nothing here enforces the service-side obligation.

## Implementation choices not fixed by the rulings

- The wire `revocation_id` sits in the unprotected COSE header under the text label `revocation_id`, outside the signed body, and is required. **Placement approved by the supervisor**, with the rationale: "The wire revocation_id is a reference value and never load-bearing; were it load-bearing, unprotected placement would violate the frozen §5 rule." The verifier recomputes the id, requires the wire value to be present and equal, and never uses it as an authorization or identity input.
- Reason codes `ARTIFACT_INTEGRITY` (artifact level) and `StatementReason` members (statement level) are separate namespaces. Alert kinds `artifact_integrity`, `invalid_revocation_statement` and `artifact_key_reuse`.
- The existing S4 reason `ARTIFACT_MALFORMED` still covers defects in the artifact envelope or body itself, before any statement is examined.

## 3. Signature classification and the policy split (final ruling)

**Dividing rule for signatures:** detectable without consulting a key is wire-malformed; requires the key is semantic. A missing signature member, a wrongly typed one and an Ed25519 signature that is not 64 bytes are wire-malformed (artifact integrity). A 64-byte signature that fails verification under the authorized key, and an unauthorized revoker, are semantic. The pinned algorithm fixes the length, so no key is needed to see a length defect. A tagged envelope that is not a four-element array is refused by the strict decoder first (defect `malformed_wire`).

**Artifact rejection is invariant across policies; the request verdict is policy-governed.**

| stage | what happens | policy-dependent |
|---|---|---|
| artifact disposition | the artifact is rejected: statements unprocessed, contents unused, high-water mark unmoved, accepted artifact not replaced, nothing persisted. It happens before the verdict and before any persistence | **no**, identical under every policy including fail-open |
| request verdict | `FAIL_CLOSED`: deny. `BOUNDED_STALENESS`: use the last authenticated artifact only while fresh, its revocations keep applying, never the rejected artifact. `FAIL_OPEN_EXPERIMENTAL`: may allow when no usable authenticated state exists (uses a fresh one if it exists). `TTL_ONLY_NO_STATUS`: excuses only an absent artifact | **yes** |

**Standing rule.** `FAIL_OPEN_EXPERIMENTAL` exists only inside an explicitly labelled experimental benchmark arm and is never a production policy or configuration option. The implementation refuses it without an `experimental_arm` label and records the label. It never overrides S3, key reuse or rollback.

**Telemetry.** `fail_open_after_status_unavailable` and `fail_open_after_artifact_integrity` are distinct findings (own alert kinds and counters; fields `finding`, `reason_code`, `experimental_arm`, `authenticated_state_used`), disjoint from every `StatusReason`. Existing `artifact_integrity` and `invalid_revocation_statement` telemetry is unchanged. A fallback to a last authenticated artifact is reported as `status_fallback_last_authenticated`.

**Proposal beyond the literal ruling:** under fail-open, a fresh last authenticated state is used instead of being discarded (the ruling allows fail-open "when no usable authenticated state exists"). This also applies after ordinary status unavailability. Reversible if the supervisor intends otherwise.

**Scope of the signature-length ruling (recorded, not extrapolated).** The supervisor's explicit signature ruling concerns revocation statements. The signature of the artifact's outer envelope is unchanged: a wrong-length outer signature is still reported as an artifact signature failure (S5, `ARTIFACT_SIGNATURE_INVALID`, mandatory alert). Both outcomes reject under every policy. The statement rule is not extended to the outer envelope unless the supervisor rules so.

**What `experimental_arm` is and is not.** It is a benchmark label and a guard against accidental selection of fail-open, written into telemetry so results can be attributed to an arm. It is not a cryptographic or production-enforcement boundary: a library cannot stop a caller from passing any string. `FAIL_OPEN_EXPERIMENTAL` remains unavailable as a production policy by rule (a production build or configuration must not offer it); the label does not make it available.

**Fail-open behavior, confirmed.** (1) A fresh last authenticated state is used and its revocations are preserved. (2) With no usable authenticated state, the labelled experimental arm may allow. (3) The rejected artifact is never used, never persisted, and never advances the high-water mark, under any policy.

**Fallback telemetry.** `status_fallback_last_authenticated` is emitted once per request decided from the last authenticated artifact, only after that state is confirmed bound to the root (so it always means the state was used). The field `policy` distinguishes `BOUNDED_STALENESS` from `FAIL_OPEN_EXPERIMENTAL`; `reason_code` names the failure that caused it; `experimental_arm` is set for fail-open. A fail-open allow with no usable state is a different alert kind (`fail_open_after_*`).

## 4. Review corrections (2026-11-15)

- **Exact reconstruction (wire-malformed).** A statement's signature is verified over its canonical reconstruction, and the strict decoder sees the embedded node envelopes only as opaque byte strings. A received payload that differs from the canonical encoding of its parsed content, for instance a non-canonical embedded node wire, is therefore `malformed_wire` and rejects the whole artifact through the artifact-integrity path. Before this correction such a statement passed as valid.
- **Unusable key material is a failed verification.** `verify_payload` returns False when the key cannot be used (for instance a subject key that is not 32 bytes) instead of raising. Inside a statement lineage this is a per-statement semantic failure (`LINEAGE_INVALID`); in a presented lineage it is a typed lineage failure. Before this correction a statement targeting a child of such a node crashed ingestion with an untyped `ValueError` after the high-water mark had already been written.
- **`reason_code` is optional.** The frozen Spec §8 calls it "Optional operational reason". It is omitted from the body when absent (never encoded as null) and, when present, must be text. **Pending supervisor confirmation.** The implementation had required it; this correction makes it optional, and an omitted `reason_code` changes the body and therefore the `revocation_id`.
- **Outer artifact signature (scope, now pinned by tests).** A wrong-length outer artifact signature is still `ARTIFACT_SIGNATURE_INVALID` (S5, mandatory alert, not `ARTIFACT_INTEGRITY`). The statement rule is not extended to it.
- **URI mismatch is unchanged and unresolved.** An authenticated artifact for the wrong URI raises `RevocationBindingMismatch` under every policy, including fail-open, although DR-1 5.1.7 says failures at steps 2 to 8 follow the unavailable-status policy. Left as is pending the supervisor.
- **Known limitations** (verifier-internal `AcceptedStatus`, non-atomic unlocked store) are recorded in DR-1 section 11.

## 5. Specification conformance fixes (2026-11-15)

- **`statement_version` must be 1 (frozen Spec §8, rule "1").** Any other value, a missing field, or a wrongly typed value (text, bool, null, bytes) is wire-malformed (`malformed_wire`) and rejects the whole artifact through the artifact-integrity path. Before this the verifier ignored the field, so a validly signed statement with `statement_version` 0, 2 or 255 took effect. This conforms the implementation to the frozen text; the Spec is unchanged. Whether a future version could be accepted is a Spec-reissue question, not an implementation default.
- **Audience is checked before status (frozen Spec §13 order: lineage, root binding, audience, attenuation, then status).** The implementation ran the status stage first, so a request that was going to be denied for audience still ingested the artifact, advanced the high-water mark and emitted status telemetry, and could surface a status error instead of the audience error. The check now runs immediately after root binding and before attenuation, as in the Spec. A request that fails the audience check no longer touches any revocation-state machinery. Visible effect: precedence between errors changes only for requests that have several defects (audience beats attenuation, and beats every status failure). Expiry is unchanged and still follows status (Revision C places it before status).
